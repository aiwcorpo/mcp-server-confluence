# AGENTS.md

mcp-confluence is the MCP server for Confluence Data Center in [MCP Platform](https://github.com/aiwcorpo/mcp-platform).
Only the gateway calls it (internal JWT, policy data pushed to `POST /.well-known/mcp-policy-data`); it calls Confluence
REST API v1 with the caller's own personal access token. Its interfaces follow `mcp-contracts`
(`server-manifest.schema.json`, `internal-jwt.schema.json`, `tool-error.schema.json`, `openapi/mcp-server.v1.yaml`) through
`mcp-platform-starter` 4.0.0 from `mcp-starter-lib`.

## Commands

Maven needs JDK 25. If `JAVA_HOME` points to an older JDK the build fails with `UnsupportedClassVersionError`; on macOS
with Homebrew use `export JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home`.

```bash
./mvnw -B verify                    # what CI runs (GitHub, GitLab, Jenkins); all tests and the manifest file
./mvnw -B -pl mcp-app -am test -Dtest=ReadToolsTest -Dsurefire.failIfNoSpecifiedTests=false   # one test class
docker build -t mcp-confluence:dev .   # image, after verify; needs a Docker daemon
```

The full verify takes about a minute. No Docker and no Confluence are needed. There is no separate lint or format step;
follow `.editorconfig`.

## Layout

- `mcp-core` (domain, ports), `mcp-application` (service, `TextDiff`), `mcp-integration` (Confluence adapter, resolvers,
  version probe, storage format), `mcp-tools` (the `@Tool` methods in `ConfluencePageTools`, `CqlConfinement`, results,
  errors), `mcp-app` (Spring Boot app, config, `ManifestExport`, policies).
- `mcp-app/src/main/resources/mcp/policies/`: the Cedar schema, `resource-types.json` and policies of the `Confluence`
  namespace.
- `mcp-app/src/test/java/.../app/`: tests of the whole server against `TestGateway` and `StubBackend`; module unit tests
  sit in each module's `src/test`. `mcp-app/target/mcp-manifest.json` is generated by the build; never edit or commit it.
- `mcp-app/src/test/resources/fixtures/confluence-dc-<version>/`: version probe answers written from vendor documentation,
  not recordings. Content responses come from `StubBackend` (see `fixtures/README.md`).

## Tool definitions are a reviewed contract

Tools, their risk classes (`@ToolRisk`), resource references and policies reach the gateway through the manifest, and
the gateway administrator approves it. A changed name, title, description, input schema, risk or `@ResourceRef` changes
the tool's `definitionHash`; a changed policy file or `resource-types.json` changes `policiesHash`. Either one puts the
server into pending approval on every installation, and calls are refused until an administrator approves again.
So: do not rename tools or reword descriptions as a side effect of other work, keep each such change in its own PR,
and name it in the CHANGELOG entry. Update `ToolListingTest`, `ConfluencePolicyDecisionsTest` and the tools table of
the README in the same change.

## Rules

- The server has no sign-in, does not decide who may call a tool and asks for no confirmation: the gateway does that.
  Do not add such checks. Resource-level decisions run in the starter's `ResourcePolicy` from the Cedar files; declare
  them with `@ResourceRef` instead of checking permissions in tool code.
- Contract first: a change that needs a different manifest field, resource type or query field starts as a `proposed`
  entry in `CONTRACT_CHANGES.md` of `mcp-contracts`, and a person approves it before it is implemented here.
- A new tool needs `@ToolTitle`, `@ToolRisk`, `@ResourceRef` for every id it names, a closed argument schema with
  bounded strings, a negative test, and a README table row.
- `search_content` is the only tool that takes CQL; `CqlConfinement` and the `space in (...)` wrapper keep it inside one
  space. Do not add another tool that passes caller text to Confluence as a query.
- A child id (comment, attachment, version) must be checked to belong to the page the policy judged.
- Writes stay closed in the `degraded` state; `MCP_CONFLUENCE_WRITES_ON_UNKNOWN_VERSION` opens them only in
  `unavailable` (`CapabilityBackendFeatures`).
- Text from Confluence goes to the model only through `UntrustedText`/`TextHygiene` from the starter.
- Map backend failures to the starter's `ToolErrorCode` in `ConfluenceToolErrors`. Never log or return the user's token
  or an `Authorization` header, and never an e-mail address in `get_page_restrictions`.
- Tests use `StubBackend` and dummy data only, never a real Confluence. Test methods are camelCase sentences
  (`theManifestPassesTheRulesOfTheGateway`).
- Add user-visible changes under `## Unreleased` at the top of `CHANGELOG.md`; the release commit renames it.
- The CI images are pinned by digest and actions by commit SHA; keep them pinned when you change them.

## Boundaries

Ask a person before you: tag, release, push to `main`, change the version in `pom.xml` or the starter version, publish an
image (images go to `ghcr.io` only, from `.github/workflows/release.yml` on a `v*` tag), or touch a real Confluence,
gateway or account. Never commit secrets, tokens, keys, certificates, filled `*.env` files (`deploy/mcp-confluence.env`
stays a template), internal host names or IP addresses.

## Pull requests

One change per PR. Commit subject in English, imperative, up to 72 characters; the body says what changed and why, not
the process. Tests go in the same commit as the code. `./mvnw -B verify` must pass. Update README, `deploy/README.md` or
the CHANGELOG when behaviour visible to users or operators changes. See [CONTRIBUTING.md](CONTRIBUTING.md).
